# 创作验收：看实际产物，记录证据边界

用于用户的个性化作品。技术可用、视觉合格、用户喜欢分别记录；当前案例的历史检查范围见 [验证历史](VERIFICATION-HISTORY.md)，不能直接继承为新作品结果。

## 观察什么

| 对象 | 合格底线 | 优秀参考 | 实际证据 |
| --- | --- | --- | --- |
| 角色理解与场景构思 | 完整创作有可追溯的主要线索、明确的场景主题和取舍；区分设定、二创解释与提案，未把名字/发色等单一标签当成全部角色 | 性格、身份或关系通过相互支持的画面选择形成个性，不堆砌设定 | 简短策划卡与成片对应；每个选中重点能指出素材、构图、动作或文案中的具体表达。有限修改按用户范围检查 |
| 人物身份与表现 | 独立主体符合参考/OC 设定与约定画风；检查适用的脸、剪影、服饰结构、配件和比例，不能只匹配名称、颜色和特征标签；没有未经允许的简化或重设计，无明显结构错误、粘连、缺损或未完成感 | 身份特征在目标尺寸下稳定，造型与细节有一致完成度 | 主体与参考/设定并列对照及关键细节；先看主体本身，再看场景 |
| 素材处理 | 独立叠合主体的透明背景有效，无明显误删/底色残留；约定的画框式呈现按其画幅边界检查 | 边缘或画框与场景自然衔接，原貌稳定 | 原图/结果对照及目标背景预览；透明主体另查深浅底，详见 [素材规格](ASSET-SPEC.md) |
| 构图 | 人物识别区域、文案和进入提示不被意外遮挡；裁切符合用户意图 | 主次清晰，留白与装饰有关系，视线与图层引导自然 | 目标宽屏、矮窗、窄窗截图，记录实际尺寸 |
| 主题视觉 | 背景、前景、纹样、装饰和文案经过有依据的取舍，与人物及所选风格相容；完整迁移不能只改配色、资源名和标签；文字可读 | 形状、材质、密度、留白和颜色共同支持表达 | 简短元素取舍记录与场景全图，检查保留旧元素的理由；不要求所有元素改变 |
| 简单代码元素 | 通过 [视觉门禁](ASSET-SPEC.md#简单代码元素的视觉门禁) 的所有适用项：设计适配、静态与动态效果均有实际观察 | 与人物及场景自然衔接，完成度不因代码实现而降低 | 本版本局部/整幅截图、宽窄窗与完整播放；逐项通过/失败/未验证/不适用 |
| 入场与停留 | 图层出现有先后，人物落位稳定；需要的局部动作不出现裂缝、穿插或截断 | 动作幅度与节奏服务人物表达，装饰不持续抢夺注意力 | 一次完整播放；有局部动作时检查极值帧和重复周期 |
| 水波交接 | 水波与画面擦除同步，结束后工作台正常显示和操作 | 交接连续，残影、突变与停顿不干扰体验 | 从点击到恢复操作的完整观察；检查不同点击起点 |
| 可复现交付 | 资源路径可用，源码与生成物对应，能从交付工程重新打开 | 新环境无需作者解释即可复现，限制交代清楚 | 基线、修改清单、命令与结果、输出位置 |

“优秀”用于指导改进，不是要求无限放大后所有像素都无瑕疵。先用实际显示尺寸判断影响，再放大具体疑点。不要自行用数字评分代替缺失的视觉证据。

策划检查按“选取准确、表达可见、元素相互支持”判断，不按搜集的条目数、阅读篇数或装饰数量评分。特点只写在策划卡里、成片没有对应表达，不能算落实；不要求所有设定都出现。若加上新元素反而削弱主题或主体，应取舍或重排。主张“有角色个性”需要画面证据，“惊艳”仍是用户对最终作品的判断。

## 先判断内容是否完成

主体身份、所需表现与主题视觉应在接入动画前分别检查；不能把人物不符或旧主题未经取舍沿用，归入“仅待用户审美确认”。这些是任务内容的失败或未验证，alpha、尺寸、构建与播放通过不能抵消。审美偏好用于比较已经符合要求的方案，也可以包含用户明确授权的风格变化。

素材来源与制作路线同样核对：角色优先使用合适的二创/原创图，可通过实际绘图/编辑能力制作；不得以手写代码拼画替代。生成图必须经过同样的角色、造型和细节检查，不能只记录“生成成功”。取得的现成矢量素材不因格式而被排除。简单元素可用代码实现，但视觉门禁失败或未验证时，不能报告效果合格。

若用户反馈“不像角色”，重查参考、独立主体与制作路线；反馈“只是改色”时，重查形状、纹样、材质及主要元素的选择。修复后展示对应的新旧对照，不重复提交同一方案的表面修饰。已有要求足够时自行修正，不把每次内部检查变成用户审批。

## 公共交互检查

按改动影响选择检查，并在新作品中保留以下公共约束：

- 用户触发退出后，点击或按键不落到工作台；特别检查长按超过视觉退出时长再释放。
- 退出后工作台可用；从设置重播后，焦点回到合适控件。
- 减少动态保留可理解的静态画面；后台暂停，卸载后监听器、动画和临时节点被清理。
- 主图缺失、可选素材缺失或加载过慢时不永久阻挡工作台。
- 新素材的首次加载与重播分别观察；只跑重播不能说明冷启动表现。

现有 `npm run test:browser` 包含“三条鱼”“飘带”“默认挥手设置”等宵宫案例断言。修改对应能力时，应将这些断言替换为新作品的可观察要求，并记录原因；保留退出、输入保护、焦点与生命周期验证。未修改案例时直接运行原检查。命令与平台差异见 [平台适配](PLATFORM-GUIDE.md)。

## 证据能支持什么

| 实际完成的工作 | 可以报告 | 不能推断 |
| --- | --- | --- |
| 读取文件、检查透明度/尺寸 | 文件结构与参数有效 | 角色身份正确、抠图干净、主题迁移完成或构图美观 |
| 构建与单元检查 | 对应代码检查通过 | 浏览器显示或原生宿主正常 |
| 浏览器截图和行为检查 | 此浏览器/视口的显示与交互结果 | 原生 DSH、另一操作系统或严格帧率 |
| 原生 DSH 观察 | 该平台、宿主版本与安装包的实际结果 | 未检查的系统、设备和版本 |
| 用户确认 | 用户对展示版本的反馈 | 其他版本或其他用户的偏好 |

没有能力观察某一层时，明确写“未验证”及原因。截图中有问题时不能只引用自动化通过；自动化失败也不能靠主观好看来覆盖。

## 最小交付记录

随作品提供一份简短记录，格式不限，包含：

- **任务与基线**：角色/风格、保留与允许改变的范围、仓库提交或版本、操作系统和相关运行环境。
- **产物**：素材、源码、生成物与预览位置；修改了哪些文件，哪些公共机制有改动及原因。
- **构思与素材**：完整创作留下简短策划卡、主要设定的来源及其画面表达，记录选中/舍弃的方向和素材理由；保留原貌对照、抠图/修边/生成等实际做法，不把生成重绘称为无损提取。
- **验收**：检查对象、命令或观察方式、结果及截图/报告位置。按“通过 / 失败 / 未验证 / 不适用”记录，不把未验证写成通过。
- **限制与下一步**：剩余问题、可行方案、用户已接受的限制；没有用户确认的限制不要代其接受。

达到本次约定的合格标准即可交付。若必要步骤缺工具、越过用户允许的修改范围或无法核验，说明具体阻碍并完成其他独立工作。素材发布许可与个人预览分开核对，不把代码 MIT 当成图像授权。
